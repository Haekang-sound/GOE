아래는 프로젝트의 아키텍처를 나타내는 다이어그램 코드입니다. 이 코드는 Mermaid Live Editor와 같은 다이어그램 렌더링 도구에 붙여넣으면 시각적인 다이어그램으로 볼 수 있습니다.

*   **GOE.exe**: 모든 엔진 모듈을 하나로 합쳐 실행하는 최종 애플리케이션입니다.
*   **GOE_Engine**: 렌더링, 에디터, 에셋 로딩 등 상위 모듈들을 총괄하고 조정하는 핵심 엔진 라이브러리입니다.

*   **GOE_AssetLoader**: Assimp 라이브러리를 통해 3D 모델과 같은 에셋을 불러옵니다.

[AI 응답: 렌더러 리소스 매니저 가이드라인 제공]
렌더러를 위한 리소스 매니저를 만드는 것은 좋은 생각입니다. 리소스 관리를 중앙화하여 중복 로딩을 방지하고, 메모리 관리를 효율적으로 할 수 있습니다.

아래에 `GOE_Render` 프로젝트를 위한 리소스 매니저 설계 및 구현 가이드라인을 제시합니다.

### **1. 리소스 매니저의 목표**

*   **중앙화**: 텍스처, 메쉬, 셰이더 등 모든 렌더링 리소스의 생성, 저장, 접근을 한 곳에서 관리합니다.
*   **중복 방지**: 동일한 리소스가 여러 번 로드되는 것을 막습니다. (예: 동일한 텍스처 파일을 두 번 로드하지 않음)
*   **수명 관리**: 리소스가 더 이상 필요 없을 때 GPU 메모리에서 안전하게 해제되도록 관리합니다.
*   **비동기 로딩 (선택 사항)**: 대용량 리소스를 로드할 때 렌더링이 멈추지 않도록 백그라운드 스레드에서 로딩을 지원합니다.

### **2. 설계 가이드라인**

#### **위치**
*   리소스 매니저는 `ID3D12Device`에 직접 접근하여 GPU 리소스를 생성해야 하므로, `GOE_Render` 프로젝트 내에 `ResourceManager` 클래스를 만드는 것이 가장 적합합니다.

#### **디자인 패턴**
*   **싱글턴 (Singleton)**: 프로젝트 전반에서 리소스 매니저에 쉽게 접근할 수 있도록 싱글턴 패턴을 적용하는 것이 편리합니다. `GOE_Core`에 이미 `SingletonBase.h`가 있으므로 이를 활용할 수 있습니다.
*   **핸들/ID 기반 시스템**: 리소스를 원시 포인터 대신 고유 ID(예: 파일 경로 문자열, 해시 값)로 식별하고 관리합니다.
    ```cpp
    // Example
    auto texture = ResourceManager::Get().GetTexture("Assets/textures/my_texture.png");
    ```

#### **핵심 구조**
*   **리소스 캐시(Cache)**: 각 리소스 타입별로 `std::unordered_map`과 같은 해시 맵을 사용하여 로드된 리소스를 저장합니다. 키는 리소스의 고유 ID, 값은 리소스 객체에 대한 스마트 포인터입니다.
    ```cpp
    // ResourceManager.h
    #include <unordered_map>
    #include <string>
    #include <memory>
    #include "Texture.h" // GOE_Core의 Texture 클래스

    class ResourceManager
    {
    private:
        std::unordered_map<std::string, std::shared_ptr<goe::Texture>> m_TextureCache;
        // ... 다른 리소스 타입 캐시 ...
    };
    ```
*   **스마트 포인터 활용**: `std::shared_ptr`를 사용하여 리소스의 수명을 자동으로 관리합니다. 해당 리소스를 사용하는 모든 객체가 사라지면 참조 카운트가 0이 되어 메모리가 자동으로 해제됩니다.

### **3. 구현 단계 (텍스처부터 시작)**

가장 일반적인 리소스인 텍스처부터 시작하여 점진적으로 확장하는 것을 추천합니다.

**1단계: `ResourceManager` 클래스 파일 생성**
*   `GOE_Render` 프로젝트에 `ResourceManager.h`와 `ResourceManager.cpp` 파일을 추가합니다.

**2단계: `ResourceManager.h` 기본 구조 작성**
```cpp
// GOE_Render/ResourceManager.h
#pragma once
#include "SingletonBase.h" // GOE_Core의 싱글턴 베이스
#include "Commons.h"       // GOE_Core의 공용 헤더
#include <string>
#include <memory>
#include <unordered_map>

// Forward declarations
struct ID3D12Device;
namespace goe { class Texture; }

class ResourceManager : public SingletonBase<ResourceManager>
{
    friend class SingletonBase<ResourceManager>;

private:
    ResourceManager() = default;
    ~ResourceManager() = default;

public:
    void Initialize(ID3D12Device* device);
    void Finalize();

    // 텍스처 로드/가져오기 함수
    std::shared_ptr<goe::Texture> GetTexture(const std::string& filePath);

private:
    // DX12 디바이스 포인터
    ID3D12Device* m_pDevice = nullptr;

    // 텍스처 리소스 캐시
    std::unordered_map<std::string, std::shared_ptr<goe::Texture>> m_textureCache;
};
```

**3단계: `ResourceManager.cpp` 구현**
```cpp
// GOE_Render/ResourceManager.cpp
#include "ResourceManager.h"
#include "Texture.h" // GOE_Core의 Texture
#include "AssetLoader.h" // GOE_AssetLoader의 로더 사용 (가정)

void ResourceManager::Initialize(ID3D12Device* device)
{
    m_pDevice = device;
}

void ResourceManager::Finalize()
{
    // 모든 리소스 캐시 클리어
    m_textureCache.clear();
}

std::shared_ptr<goe::Texture> ResourceManager::GetTexture(const std::string& filePath)
{
    // 1. 캐시에서 파일 경로(ID)를 찾아본다.
    auto it = m_textureCache.find(filePath);
    if (it != m_textureCache.end())
    {
        return it->second; // 2. 찾았으면 캐시된 리소스를 반환한다.
    }

    // 3. 캐시에 없으면 새로 로드한다.
    // AssetLoader를 사용해 이미지 파일을 로드하고 DX12 텍스처 리소스를 생성합니다.
    // (이 부분은 기존 텍스처 로딩 코드를 재활용하거나 새로 작성해야 합니다)
    auto newTexture = std::make_shared<goe::Texture>();
    if (newTexture->Load(m_pDevice, filePath)) // Load 함수는 DX12 리소스 생성 로직 포함
    {
        // 4. 로드에 성공하면 캐시에 저장하고 반환한다.
        m_textureCache[filePath] = newTexture;
        return newTexture;
    }

    // 5. 로드 실패 시 nullptr 반환
    // (또는 기본 에러 텍스처를 반환하는 것도 좋은 방법입니다)
    return nullptr;
}
```

**4단계: 엔진에 통합**
1.  엔진 초기화 시점에서 `ResourceManager::Get().Initialize(device);`를 호출합니다.
2.  엔진 종료 시점에서 `ResourceManager::Get().Finalize();`를 호출합니다.
3.  기존 코드에서 텍스처를 개별적으로 로드하던 부분을 모두 `ResourceManager::Get().GetTexture(...)` 호출로 변경합니다.

### **4. 다음 단계**

텍스처 관리가 성공적으로 구현되면, 동일한 패턴을 **메쉬(Mesh)**, **셰이더(Shader)**, **머티리얼(Material)**, **PSO(Pipeline State Object)** 등 다른 리소스 타입으로 확장해 나갈 수 있습니다. 특히 PSO와 같이 생성 비용이 비싼 객체를 캐싱하면 성능 향상에 큰 도움이 됩니다.

[AI 요약: `ResourceManager`와 `PSOManager` 설계를 시작으로, 싱글턴 패턴의 단점을 피하기 위한 아키텍처 개선에 대한 심도 깊은 논의를 진행함.]

**주요 논의 내용:**

1.  **싱글턴 패턴의 대안**:
    *   사용자가 싱글턴 남용에 대한 우려를 표함.
    *   이에 대한 해결책으로, 모든 렌더링 관련 시스템(매니저)들의 포인터를 담는 중앙 허브 역할의 `RenderContext` 구조체(서비스 로케이터 패턴)를 제안함.
    *   이 방식은 전역 상태를 없애고, 시스템 간의 의존성을 명확히 하며, 초기화 순서를 완벽하게 제어할 수 있는 장점이 있음.

2.  **`RenderContext` 아키텍처 정립**:
    *   **소유권 모델**: `GOERenderer` 클래스가 `ResourceManager`, `PSOManager` 등 모든 하위 매니저들을 `std::unique_ptr`로 소유하고, `RenderContext`는 이 매니저들에 대한 non-owning 포인터를 담는 접근점으로 사용하기로 함. 이는 RAII 원칙과 캡슐화를 잘 따르는 좋은 설계임.
    *   **정의 위치**: `RenderContext` 구조체는 `GOE_Render` 프로젝트 내에 `RenderContext.h`라는 별도의 헤더 파일로 만드는 것이 가장 깔끔하다고 결론 내림.
    *   **이름 결정**: 사용자의 취향에 따라 `RenderServices` 대신 `RenderContext`라는 이름을 사용하기로 함.

3.  **구현 디테일**:
    *   **긴 호출 체인 문제**: `m_renderContext.get()->m_manager->Function()`과 같은 긴 호출은 가독성이 떨어지므로, 함수 내에서 `auto& context = *m_renderContext;` 와 같이 지역 참조를 사용해 코드를 간결하게 만들기로 함.
    *   **퍼사드 패턴**: `GOERenderer`가 `LoadTexture` 같은 함수를 직접 가지고 내부적으로 `ResourceManager`를 호출하는 방식(퍼사드 패턴)에 대한 고민을 나눔. 이는 렌더링 시스템의 복잡성을 외부에 숨기고 API를 단순하게 유지하는 좋은 장기적 설계라는 점에 동의함.

4.  **오류 디버깅**:
    *   사용자가 `m_renderContext.get()->m_UIManager` 호출 시 발생하는 오류에 대해 질문함.
    *   가장 유력한 원인으로 `RenderContext` 구조체 내의 `m_UIManager` 포인터가 할당되지 않은(nullptr) 상태일 가능성을 지적함. `GOERenderer` 초기화 시점에 `UIManager` 인스턴스를 생성하고, 그 포인터를 `RenderContext`에 명시적으로 넣어주는 해결책을 제시함.

[AI 요약: 렌더러 아키텍처 심층 분석 및 리팩토링 계획 수립]

애니메이션 데이터 흐름에 대한 질문으로 시작하여, 렌더러의 전체 아키텍처를 심층적으로 분석하고 개선 방향을 정립했다.

**주요 논의 내용:**

1.  **문제점 발견**:
    *   `ResourceManager`와 `GOERenderer`에서 가장 시급하고 심각한 아키텍처 문제점을 발견했다.
    *   `LoadTexture`, `CreateCBResource` 등에서 텍스처나 상수 버퍼 같은 **리소스를 생성할 때마다 매번 개별 디스크립터 힙을 생성**하고 있었다.
    *   이로 인해 `GOERenderer`의 렌더링 루프 안에서 매 오브젝트마다 `SetDescriptorHeaps`를 호출하는, **성능에 매우 치명적인 작업**이 수행되고 있었다.

2.  **'전문가 팩토리' 아키텍처 정립**:
    *   하나의 클래스가 모든 것을 관리하는 '신의 객체'를 피하기 위해, 역할과 책임에 따라 관리 주체(팩토리)를 명확히 분리하기로 합의했다.
    *   **`ResourceManager` (데이터 팩토리):** 버퍼, 텍스처, 컴파일된 셰이더 등 순수 '데이터' 리소스의 생성과 보관을 책임진다.
    *   **`PSOManager` (상태 팩토리):** PSO, 루트 시그니처 등 '어떻게 그릴 것인가'를 정의하는 '상태' 객체의 생성과 보관을 책임진다. (셰이더는 `ResourceManager`에서 가져와 사용)
    *   **`SwapChain` (출력 팩토리):** 백 버퍼, RTV 등 최종 '화면 출력'에 관련된 리소스를 책임진다.

3.  **범용 상수 버퍼 생성 함수 설계**:
    *   `ResourceManager`의 역할을 강화하기 위한 첫 단계로, 범용 상수 버퍼 생성 함수를 설계했다.
    *   이 함수는 `const void* initialData` (데이터 시작 주소)와 `size_t bufferSize` (데이터 크기)만 인자로 받아, 데이터의 실제 타입과 무관하게 `ID3D12Resource`를 생성한다.
    *   핵심은 이 함수가 **리소스 생성 책임만** 지고, 디스크립터 힙 생성이나 뷰(CBV) 생성 책임은 지지 않는다는 것이다.

**다음 단계:**

*   `ResourceManager`에 범용 상수 버퍼 생성 함수를 구현하고, 기존의 비효율적인 코드를 리팩토링하는 작업을 진행하기로 함.

### **아키텍처 리팩토링 논의 요약 및 결정 사항**

**배경:**
기존 `GOE_Render`의 리소스 관리 방식은 각 리소스(텍스처, 메쉬)가 개별적인 디스크립터 힙을 생성하고 소유하는 구조였습니다. 이는 언리얼 엔진의 D3D12 리소스 관리 흐름("언리얼 탐구.txt" 파일 분석)과 비교했을 때, 비효율적인 디스크립터 힙 생성 및 잦은 `SetDescriptorHeaps` 호출로 인한 성능 저하 문제를 야기할 수 있음이 지적되었습니다.

**문제점:**
*   `LoadTexture` 등에서 리소스 로드 시마다 개별 `ID3D12DescriptorHeap` 생성.

1.  **`ResourceManager`의 역할 재정의 (데이터 소유 및 관리):**
    *   모든 `ID3D12Resource` (정점 버퍼, 인덱스 버퍼, 상수 버퍼, 텍스처 등)의 **생성 및 소유**를 전담합니다.

    *   이들 객체는 더 이상 `ID3D12Resource`나 `ID3D12DescriptorHeap` 자체를 소유하지 않습니다.

*   `MeshResource` 및 `RenderObject`의 상수 버퍼 관리 로직도 동일한 방식으로 리팩토링.

### D3D12 런타임 에러 디버깅 및 동기화 문제 해결

**문제 상황:**
`ResourceManager`와 `CommandContext` 수정 후, 프로그램 실행 시 D3D12 런타임 에러가 다수 발생하며 애플리케이션이 강제 종료됨. 주요 에러는 다음과 같음:
- `COMMAND_ALLOCATOR_SYNC`: GPU가 사용 중인 Command Allocator를 리셋 시도.
- `OBJECT_DELETED_WHILE_STILL_IN_USE`: GPU가 사용 중인 리소스를 CPU에서 미리 해제.
- `RESOURCE_BARRIER_BEFORE_AFTER_MISMATCH`: 리소스 상태 장벽의 상태 정보 불일치.

**원인 분석:**
- 에러들의 근본 원인은 **CPU와 GPU 간의 동기화 실패**로 진단됨.
- 리소스 생성 시, 데이터 복사를 위해 생성된 임시 업로드 버퍼가 GPU의 복사 작업이 끝나기도 전에 CPU에서 먼저 해제되고 있었음.
- 이로 인해 연쇄적으로 동기화 문제가 발생하며 모든 에러가 파생됨.

**해결 과정:**

1.  **Resource Barrier 수정:** `CommandContext.cpp`에서 리소스 복사 후의 상태 장벽(Resource Barrier)이 실제 리소스 상태(`COPY_DEST`)와 일치하지 않는 문제를 수정함.

2.  **동기식 처리로 전환:** 리소스 생성 과정이 끝날 때까지 CPU가 명시적으로 기다리도록 동기화 로직을 추가함.
    - `CommandContext::CopyResource` 함수가 GPU 작업 완료를 식별할 수 있는 '펜스 값(Fence Value)'을 반환하도록 수정.
    - `ResourceManager`의 리소스 생성 함수(`CreateVBResource`, `CreateIBResource`, `LoadTexture`)들에서, GPU에 복사 명령을 내린 직후 반환된 펜스 값을 사용해 `WaitForFence`를 호출.
    - 이 조치로 GPU 복사 작업이 100% 완료된 후에야 다음 코드가 실행되도록 보장하여, 리소스 조기 해제 및 모든 동기화 문제를 해결함.

**결론:**
D3D12의 비동기 실행 모델을 다룰 때, 리소스의 생명 주기와 GPU 타임라인을 정확히 일치시키는 동기화 작업이 매우 중요함을 재확인함. 이번 디버깅을 통해 펜스(Fence)를 이용한 명시적 동기화의 필요성과 구현 방법을 명확히 함.

    *   `GOERenderer`가 렌더링 시 리소스의 상태를 확인하여, `Ready` 상태일 때만 그리도록 조건문을 추가하는 단계를 논의했다.

### **비동기 리소스 로딩 시스템 구축 완료 (feat. Gemini-AI)**

**목표:** 기존의 동기식 리소스 로딩은 로딩 중 게임 전체를 멈추게 만들어 사용자 경험을 저해했다. 이를 게임 루프를 막지 않는 비동기(Asynchronous) 방식으로 전환하고, 그 과정에서 발생하는 동기화 문제를 해결하여 안정적인 시스템을 구축하는 것을 목표로 삼았다.

**1단계: 비동기 구조로의 전환**

1.  **논블로킹(Non-blocking) 전환:** `LoadTexture`, `CreateVBResource` 등 리소스 생성 함수들에서 GPU의 완료를 무작정 기다리던 `WaitForCopyFence()` 코드를 제거하여, CPU가 명령만 내리고 즉시 다음 작업을 수행하도록 변경했다.
2.  **상태 관리 시스템 구축:**
    *   리소스에 `LOADING`, `READY` 상태를 추가했다.
    *   `ResourceManager`에 `UpdateResourceStates()` 함수를 구현했다. 이 함수는 매 프레임 GPU의 펜스(Fence) 값을 확인하여, 복사가 완료된 리소스의 상태를 `READY`로 전환하는 역할을 맡는다.
    *   `GOERenderer::OnUpdate`에서 `UpdateResourceStates()`를 호출하여 매 프레임 상태가 갱신되도록 연결했다.
3.  **안전한 렌더링:** `GOERenderer::OnRender`에서 리소스를 그리기 전에 상태가 `READY`인지 확인하는 `if`문을 추가했다. 이를 통해 아직 데이터 준비가 덜 끝난 리소스를 그리려다 발생하는 비정상 종료를 방지했다.

**2단계: `COMMAND_ALLOCATOR_SYNC` 오류 발생 및 해결**

1.  **문제 발생:** 비동기 전환 직후, `Command Allocator`를 GPU가 아직 사용 중인 상태에서 `Reset`하려 한다는 `COMMAND_ALLOCATOR_SYNC` 오류가 발생했다. CPU가 GPU의 작업 속도보다 빨라지면서 생긴 전형적인 경쟁 상태(Race Condition)였다.
2.  **해결 - 'Wait-and-Reset' 패턴 구현:**
    *   `GraphicsDevice`에 특정 펜스 값까지 대기할 수 있는 `WaitForCopyFenceValue(UINT64 fenceValue)` 함수를 추가하여 정밀한 동기화가 가능하도록 기반을 마련했다.
    *   `CopyCommandContext::Reset()` 함수를 재정의(override)했다. 새로운 `Reset` 함수는 내부적으로 `WaitForCopyFenceValue`를 호출하여, **자신이 마지막으로 제출했던 작업**이 끝났음을 확인한 후에만 안전하게 할당자(Allocator)를 초기화하도록 수정했다.

**최종 결과:**
이 일련의 과정을 통해, 게임 루프를 방해하지 않으면서도 백그라운드에서 안전하게 리소스를 로딩하는 견고한 비동기 시스템을 구축하는 데 성공했다. 전역 대기(Global Wait)를 없애는 대신, 꼭 필요한 자원(Allocator)에 대해서만 최소한의 동기화를 수행하는 효율적인 구조를 완성했다.

### **기술적 회고: D3D12 Descriptor Management 최적화**

#### **1. 핵심 아키텍처 변화**

*   **기존 (Individual Heaps):**
    *   각 `Resource`(Texture, Mesh)가 자신만의 소형 `Descriptor Heap`을 개별적으로 소유.
    *   **문제점:** Draw Call마다 서로 다른 힙을 바인딩하기 위해 `SetDescriptorHeaps`를 빈번하게 호출. 이는 GPU 파이프라인의 병목(Pipeline Stall)을 유발하는 고비용 연산임.

*   **변경 (Centralized & Dynamic Heap):**
    *   **Staging Heap (Static):** `D3D12_DESCRIPTOR_HEAP_FLAG_NONE`. 리소스 로딩 시 생성된 디스크립터를 영구 보관하는 CPU 전용 힙. 셰이더 접근 불가.
    *   **Rendering Heap (Dynamic):** `D3D12_DESCRIPTOR_HEAP_FLAG_SHADER_VISIBLE`. 매 프레임 `Reset`되는 Ring Buffer 구조. 셰이더가 참조하는 유일한 힙.
    *   **최적화:** 프레임 시작 시 `SetDescriptorHeaps`를 **단 1회** 호출. 모든 리소스 뷰(SRV, CBV)를 Rendering Heap으로 **복사(CopyDescriptors)**하거나 **즉시 생성(CreateView)**하여 바인딩.

#### **2. Descriptor Copy & Binding 메커니즘**

*   **CopyDescriptorsSimple (Device API):**
    *   서로 다른 힙 간에 디스크립터 정보를 복사하는 기능.
    *   **Source:** Staging Heap (CPU Readable).
    *   **Dest:** Rendering Heap (CPU Writable, GPU Readable).
    *   이 기능을 통해 흩어져 있는 정적 리소스들의 뷰를 렌더링 힙의 연속된 메모리 공간으로 모음 → **공간 지역성(Spatial Locality)** 극대화로 GPU 캐시 적중률 향상.

#### **3. 트러블슈팅 (Troubleshooting)**

*   **Error 1: `SET_DESCRIPTOR_HEAP_INVALID`**
    *   **원인:** `SetDescriptorHeaps`에 동일한 타입(`CBV_SRV_UAV`)의 힙 2개를 동시에 전달 시도. D3D12 명세상 타입별 1개의 힙만 활성화 가능.
    *   **해결:** Rendering Heap 하나만 바인딩하고, Staging Heap의 내용은 복사해서 사용하는 방식으로 전환.

*   **Error 2: `COPY_DESCRIPTORS_WRITE_ONLY_DESCRIPTOR`**
    *   **원인:** Staging Heap을 `SHADER_VISIBLE`로 생성함. 이 플래그가 켜진 힙은 CPU 입장에서 **Write-Combine** 메모리로 취급되어 **Read(복사 원본으로 사용)**가 불가능하거나 매우 느림.
    *   **해결:** Staging Heap의 플래그를 `D3D12_DESCRIPTOR_HEAP_FLAG_NONE`으로 변경하여 CPU Read/Write가 자유로운 일반 메모리처럼 취급.

*   **Error 3: `DESCRIPTOR_HEAP_NOT_SHADER_VISIBLE`**
    *   **원인:** `FLAG_NONE`으로 바뀐 Staging Heap에 대해 `GetGPUDescriptorHandleForHeapStart()` 호출. 셰이더에 안 보이는 힙은 GPU 가상 주소(GPU Handle)를 가지지 않음.
    *   **해결:** Staging Heap은 CPU Handle만 사용하도록 로직 수정.

#### **4. 최종 성과**
*   **Draw Call Overhead 최소화:** 힙 변경 비용 제거.
*   **Memory Management:** 동적 데이터(Animation Bone Matrix)를 위한 별도 버퍼 관리 없이, 렌더링 힙의 남는 공간을 스택처럼 활용하는 **Linear Allocation** 패턴 정착.

### **D3D12 아키텍처 진화: RenderObject 경량화 및 동적 상수 버퍼 할당**

**문제 상황:**
`RenderSystem`의 `Update` 단계에서 `RenderObject`를 생성할 때, 상수 버퍼(CB) 리소스를 생성하지 않아 `nullptr` 접근 오류(Access Violation)가 발생했다.

**논의 및 해결 방향:**

1.  **`RenderObject`의 정체성 재정립:**
    *   기존에는 `RenderObject`가 자신만의 `ID3D12Resource`(CB)를 소유하는 무거운 객체였다.
    *   이는 매 프레임 생성/파괴 비용이 크고 비효율적이라는 결론에 도달했다.
    *   따라서 `RenderObject`를 순수 데이터(MeshID, Matrix 등)만 담고 있는 **가벼운 구조체(Value Object)**로 취급하기로 결정했다.

2.  **동적 상수 버퍼(Dynamic Constant Buffer) 도입:**
    *   개별 객체가 CB를 갖는 대신, 렌더러가 관리하는 **거대한 업로드 힙(Upload Heap)** 하나를 사용하여 매 프레임 데이터를 처리하기로 했다.
    *   **작동 방식:**
        1.  `DescriptorHeapManager`에 `AllocateDynamicConstantBuffer(data, size)` 함수를 추가한다.
        2.  이 함수는 힙 메모리에 데이터를 `memcpy`하고, 즉시 사용 가능한 GPU 가상 주소를 반환한다.
        3.  렌더링 시점에 이 주소를 `SetGraphicsRootConstantBufferView`에 전달한다.

3.  **렌더링 파이프라인 최적화:**
    *   `RenderSystem::Update`에서는 오직 데이터 수집과 스키닝(본 행렬 계산)만 수행하고, 리소스 생성은 하지 않는다.
    *   `GOERenderer::OnRender`에서 그리는 순간에 필요한 메모리를 즉석에서 할당받아 사용한다.

**결론:**
이러한 구조 변경을 통해 `RenderObject` 생성 비용을 '0'에 가깝게 줄이고, 수천 개의 오브젝트를 효율적으로 처리할 수 있는 **Stateless Rendering** 아키텍처로 나아가는 발판을 마련했다.

### **카메라 시스템 컴포넌트화 및 Input/Time 시스템 통합 완료**

**배경:**
기존 `Camera` 클래스는 렌더러에 종속된 임시 객체였으며, 입력 처리도 `GetAsyncKeyState`로 하드코딩되어 있었다. 엔진의 ECS 구조에 맞게 이를 정식 컴포넌트로 승격시키고, 기 구현된 `InputManager`와 `TimeManager`를 적용하여 시스템을 통합할 필요가 있었다.

**주요 작업 내용:**

1.  **CameraComponent 도입 (ECS 통합):**
    *   `GOE_Engine`에 `IComponent`를 상속받는 `CameraComponent`를 신규 생성했다.
    *   `CameraComponent`는 순수 데이터(FOV, Near/Far, Aspect)만 관리하고, 행렬 계산 로직은 렌더러로 위임하여 역할을 분리했다.
    *   `Scene` 클래스에 `CameraComponent` 매니저를 추가하고, 스크립트 단계에서 카메라 엔티티를 생성하도록 초기화 로직을 수정했다.

2.  **Input & Time 시스템 적용 (MovementSystem 리팩토링):**
    *   `MovementSystem`을 대대적으로 리팩토링하여 `InputManager`와 `TimeManager`를 기반으로 동작하도록 수정했다.
    *   **자유 시점 카메라 (Free Camera):** W/A/S/D 이동 및 마우스 우클릭 회전(Yaw/Pitch)을 구현하고, `DeltaTime`을 적용하여 프레임 독립적인 움직임을 보장했다.
    *   **Transform 개선:** `Transform` 컴포넌트에 `SetRotation`, `SetPosition` 등을 추가하여 행렬을 안전하게 재구성(`UpdateTransform`)하도록 수정했다. 특히 기저 벡터 추출 시 열(Column) 대신 행(Row)을 읽도록 수정하여 회전 후 이동이 꼬이는 문제를 해결했다.

3.  **렌더링 파이프라인 최적화 (Engine-Renderer 분리):**
    *   `GOERenderer`에서 `Camera` 클래스에 대한 직접 의존성을 제거했다.
    *   대신 `SetCameraData` 인터페이스를 통해 엔진(`RenderSystem`)으로부터 순수 데이터(World Matrix, FOV 등)를 주입받도록 구조를 변경했다.
    *   **SIMD 가속 활용:** 뷰/프로젝션 행렬 계산을 엔진(`CoreMath`)에서 하지 않고, 렌더러 내부에서 `DirectXMath` (SIMD 지원)를 사용하여 수행함으로써 성능과 안정성을 확보했다.

4.  **수학 라이브러리 독립성 확보:**
    *   `CoreMath.h`에서 `DirectXMath` 의존성을 완전히 제거하고, 순수 C++ (`cmath`) 기반으로 수학 함수들을 재구현하거나 정리했다. 이를 통해 코어 모듈의 플랫폼 독립성을 유지했다.
